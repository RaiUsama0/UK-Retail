# Public Dataset — Privacy Review

Generated by `ingest-data export-public` (`src/ecommerce_analytics/public_export.py`),
verified against a live PostgreSQL instance at export time. **These 15 CSVs are
committed to git** (unlike the internal Power BI export in
`dashboards/powerbi/data/`, which is gitignored) because Streamlit Community Cloud
has no PostgreSQL access — the deployed app can only serve what's in the repo. This
is safe specifically because every file here is small and aggregate-only (see below);
a 541,909-row internal fact table would never be committed this way. Regenerate with
`ingest-data export-public` and commit the update after any upstream pipeline change.

## The rule enforced by every file here

**No file in this directory contains a `customer_id` or `customer_key` column, or any
per-customer/per-transaction row.** This is checked automatically
(`public_export.assert_no_customer_identifiers`, run as part of the export CLI
command, and as its own test in `tests/test_public_export.py`) — not just a one-time
manual review.

## Internal warehouse vs. public extracts — the actual difference

| | Internal (Power BI, `dashboards/powerbi/data/`) | Public (this folder) |
|---|---|---|
| `fact_sales` | Full transaction grain, `customer_key` per row | **Not included** |
| Customer data | `v_customer_rfm` — one row per customer, with `customer_id` | Only 5-row segment summaries and 10-row spend deciles — no `customer_id` anywhere |
| Purpose | Internal analytical tool | Public portfolio demo |

## Per-file grain and privacy rationale

| File | Grain | Rows | Contains customer data? |
|---|---|---|---|
| `product_performance.csv` | One row per product | 3,921 | No |
| `product_monthly_trend.csv` | Product x month | 34,068 | No |
| `product_cancellation_activity.csv` | One row per product with >=1 cancellation | ~1,947 | No |
| `product_country_performance.csv` | Product x country, **top 20 per country only** | ~757 | No |
| `country_performance.csv` | One row per country | 38 | No |
| `monthly_revenue.csv` | One row per month | 13 | No |
| `cohort_retention.csv` | Cohort-month x activity-month | 91 | No individual customer — counts only |
| `duplicate_sensitivity.csv` | One row per dataset version | 2 | No |
| `transaction_quality_summary.csv` | One row per transaction_status | 4 | No |
| `anomalous_transactions.csv` | The 3 anomalous-invoice-format rows | 3 | No — `customer_id`/`customer_key`/`source_row_id` deliberately excluded from the export query, even though these 3 specific rows have no customer attached anyway |
| `customer_segment_summary.csv` | One row per RFM segment | 5 | **Aggregated only** — count and averages, never an individual |
| `customer_spend_deciles.csv` | One row per spend decile | 10 | **Aggregated only** |
| `customer_headline_metrics.csv` | One row, whole dataset | 1 | **Aggregated only** — scalars |
| `dataset_metadata.csv` | One row, whole dataset | 1 | No |
| `dim_product.csv` | One row per product | 4,070 | No |

## Why some views were trimmed rather than published in full

`product_country_performance.csv` is `warehouse.v_product_country_rankings` filtered
to `rank_within_country <= 20` (not the full ~19,657-row cross-join) — this keeps the
public dataset small and the "country-level product performance" page focused, with
no privacy motivation (this view never touched customer data either way).
